# Database Design & Scripting Rules

## 1. Naming Conventions
- **Tables**:
  - Lowercase `snake_case`, plural form.
  - Examples: `dealerships`, `service_bays`, `technicians`, `technician_skills`, `appointments`, `appointment_audit_logs`.
- **Columns**:
  - Lowercase `snake_case`, descriptive, no ambiguous abbreviations.
  - Examples: `dealership_id`, `start_time`, `end_time`, `duration_minutes`, `reference_number`.
- **Primary Keys (PK) - Pragmatic Hybrid Key Architecture**:
  - Always named `id`.
  - **Master & Reference Catalog Data** (`dealerships`, `service_types`, `service_bays`, `technicians`, `technician_skills`, `customers`): Data type `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` combined with unique natural business `code`s (`code`, `customer_code`, `employee_code`). Optimizes B-Tree index node size, provides human-readable IDs (`1, 2, 3...`), and eliminates artificial UUIDs in seed migrations.
  - **Transactional Domain Data** (`appointments`, `appointment_audit_logs`): Data type `UUID PRIMARY KEY DEFAULT gen_random_uuid()`. Eliminates IDOR attack vectors and prevents public enumeration of appointment velocity.
  - Constraint naming: `pk_{table_name}` (e.g. `pk_appointments`).
- **Foreign Keys (FK)**:
  - Column name: `{singular_referenced_table}_id`.
  - Constraint naming: `fk_{table_name}_{referenced_table}_{column_name}`.
  - Example: `fk_appointments_service_bays_bay_id`.
- **Indexes**:
  - Index name prefix: `idx_{table_name}_{column(s)}`.
  - Example: `idx_appointments_dealership_time_range`, `idx_appointments_bay_time`.
- **Unique Constraints**:
  - Constraint name prefix: `uk_{table_name}_{column(s)}`.
  - Example: `uk_appointments_reference_number`.
- **Check Constraints**:
  - Constraint name prefix: `chk_{table_name}_{purpose}`.
  - Example: `chk_appointments_status`, `chk_appointments_time_validity`.

---

## 2. Data Types & Column Specifications
- **Strings**:
  - Never use unbounded `VARCHAR`. Always specify a realistic maximum length.
  - Vehicle VIN: `VARCHAR(17)` (ISO 3779 standard).
  - Reference Code: `VARCHAR(32)`.
  - Short names / titles: `VARCHAR(100)` or `VARCHAR(150)`.
  - Descriptions: `VARCHAR(500)` or `TEXT`.
- **Timestamps**:
  - Never use timezone-unaware `TIMESTAMP`.
  - Always use `TIMESTAMP WITH TIME ZONE` (`TIMESTAMPTZ`) to ensure uniform handling across dealerships in different timezones.
- **Enums & Classifications**:
  - Store as `VARCHAR(30)` with a database `CHECK CONSTRAINT`.
  - Example: `CHECK (status IN ('CONFIRMED', 'IN_PROGRESS', 'COMPLETED', 'CANCELLED', 'RESCHEDULED'))`.
- **Numeric & Durations**:
  - Service duration: `INT` with `CHECK (duration_minutes > 0)`.
  - Version column: `INT NOT NULL DEFAULT 0` (for optimistic locking).

---

## 3. Mandatory Audit Columns
Core domain and transactional tables must include:
1. `created_at`: `TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP`
2. `updated_at`: `TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP`
3. `version`: `INT NOT NULL DEFAULT 0`

---

## 4. Indexing & Concurrency Strategy
- **Foreign Key Indexing**: Every foreign key column must have a backing index to prevent full table scans on joins.
- **Temporal Overlap Queries**:
  - For checking schedule conflicts `(start_time < :endTime AND end_time > :startTime)`, create composite indexes:
    - `CREATE INDEX idx_appointments_bay_time ON appointments (service_bay_id, start_time, end_time);`
    - `CREATE INDEX idx_appointments_tech_time ON appointments (technician_id, start_time, end_time);`
    - `CREATE INDEX idx_appointments_dealer_time ON appointments (dealership_id, start_time, end_time);`
- **Pessimistic Locking**:
  - Appointment reservation queries must use pessimistic row locking (`SELECT ... FOR UPDATE` via `@Lock(LockModeType.PESSIMISTIC_WRITE)`).
- **Active Appointments Only**:
  - Only active reservations (`CONFIRMED`, `IN_PROGRESS`) occupy bay and technician time. `CANCELLED` bookings immediately release resources.

---

## 5. Flyway Migration Rules
- **File Naming**:
  - `V{version}__{description}.sql` (strictly 2 underscores).
  - Integer sequential numbering: `V1__init_schema.sql`, `V2__seed_data.sql`.
- **Immutability & Idempotence**:
  - Migration scripts must never be altered once committed and executed.
  - Use defensive syntax: `CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`.
- **Separation of Concerns**:
  - DDL schema in `V1`, seed data in `V2`.

---

## 6. Deterministic Query Ordering & Sorting Strategy
- **Deterministic Sort Standard (Code first, then Name)**:
  - Every SQL / JPQL query that returns a list or page of records must specify an explicit, deterministic `ORDER BY` clause.
  - Standard catalog sorting order:
    - `dealerships`: `ORDER BY code ASC, name ASC`
    - `service_types`: `ORDER BY code ASC, name ASC`
    - `technicians`: `ORDER BY employee_code ASC, last_name ASC, first_name ASC`
    - `service_bays`: `ORDER BY bay_number ASC, name ASC`
    - `customers`: `ORDER BY customer_code ASC, last_name ASC, first_name ASC`
    - `appointments`: `ORDER BY start_time DESC, reference_number ASC`
- **Index Support for Ordering & Pagination**:
  - Where frequent paginated searches occur (e.g. active catalog queries), composite B-Tree indexes should align with filter-and-sort patterns to avoid costly in-memory sort buffers (`Sort` operations in query plans).
